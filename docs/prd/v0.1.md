# PRD: miruca 0.1

全体の構成図は [docs/architecture.md](../architecture.md) にある。

## 目的

miruca は、チームの開発の流れをコードホスティングサービスのデータから数字で見せるサービスです。0.1 では、開発者が GitHub でログインして自分のリポジトリの PR リードタイムを見られることと、GitHub のアカウントを持たないマネージャーが組織のすべてのリポジトリの PR リードタイムを見られることを作ります。

0.1 で確かめたいのは次の3つです。

- GitHub App のインストールから最初の数字を見るまでの流れが、組織の管理者と開発者にとって迷わないか。
- 招待されたマネージャーが、GitHub のアカウントなしで、組織全体の数字までたどり着けるか。
- 1つの数字（PR リードタイム）が、チームとマネージャーが振り返りに使える形で出せるか。

## 使う人

| 人 | GitHub のアカウント | やること |
| --- | --- | --- |
| 組織の管理者 | ある（miruca から GitHub App をインストールした人） | 組織に miruca の GitHub App をインストールする。マネージャーを招待する。組織のすべてのリポジトリを見る |
| 開発者 | ある | GitHub でログインし、GitHub 上でアクセスできるリポジトリの数字を見る |
| マネージャー | ない | 招待メールからメールアドレスでログインし、組織のすべてのリポジトリの数字を見る |

## 範囲

### 0.1 に入れるもの

1. GitHub でログインする、ログアウトする。
2. メールアドレスでログインする（招待された人だけ）。
3. 組織の管理者が、メールアドレスを指定してマネージャーを招待する。招待を取り消す。
4. 自分が見られる組織とリポジトリの一覧を見る。
5. 選んだリポジトリの、直近30日にマージされた PR のリードタイムを見る。

### 0.1 に入れないもの

- メールアドレス以外の、GitHub を使わないログイン手段（Google、Microsoft、SAML など）。
- 招待した人を、一部のリポジトリやチームだけに絞って見せること。
- GitLab など GitHub 以外のサービスへの対応。
- 定期的なデータ収集と保存。表示のたびに GitHub API を呼ぶ。
- 複数のリポジトリをまとめた集計、チーム単位の集計。
- PR リードタイム以外の指標（レビュー時間、スループット、DORA）。
- グラフ、期間の切り替え、CSV の出力。
- 課金。

最初の3つは、0.1 の作りで後から足せるようにする（「将来の拡張に向けた前提」を参照）。残りは 0.1 を使った人の反応を見てから、別の PRD か Issue で扱う。

## 使う人の流れ

### 組織の管理者

1. miruca を開き、「GitHub でログイン」を押す。
2. 「組織をつなぐ」から GitHub App「miruca」を組織にインストールし、対象のリポジトリを選ぶ。
3. miruca に戻ると、その人がつないだ組織の管理者になり、組織のすべてのリポジトリが一覧で出る。
4. 「メンバーを招待」からマネージャーのメールアドレスを入れて招待する。

### 開発者

1. miruca を開き、「GitHub でログイン」を押す。
2. GitHub 上でアクセスできるリポジトリが一覧で出る。
3. リポジトリを選ぶと、PR リードタイムが出る。

### マネージャー

1. 招待メールのリンクを開く。
2. 「ログイン用のリンクを送る」を押す。届いたメールのリンクを開くとログインできる。
3. 組織のすべてのリポジトリが一覧で出る。
4. リポジトリを選ぶと、PR リードタイムが出る。

2回目からは、miruca のログイン画面でメールアドレスを入れ、届いたリンクからログインする。

## 用語

| 用語 | 意味 |
| --- | --- |
| ユーザー | miruca に登録された人。miruca が ID を発行する。GitHub のアカウントとは別のもの |
| ログイン手段 | ユーザーがログインに使うもの。0.1 では GitHub のアカウントとメールアドレスの2種類 |
| 組織 | miruca 上の会社やチームの単位。miruca が ID を発行する |
| 接続 | 組織とコードホスティングサービスのつながり。0.1 では GitHub App のインストール |
| 所属 | ユーザーが組織で持つ役割。0.1 では「管理者」と「全体を見る人」の2種類 |
| リポジトリ | 接続を通して見えるリポジトリ。miruca が ID を発行する |
| PR | GitHub の Pull Request。将来は GitLab の Merge Request も PR として扱う |

## 見られる範囲

| 人 | 所属 | 見られるリポジトリ |
| --- | --- | --- |
| 組織の管理者 | 管理者 | 組織のすべてのリポジトリ |
| マネージャー | 全体を見る人 | 組織のすべてのリポジトリ |
| 開発者 | なし | GitHub 上でアクセスできるリポジトリ |

- 「組織のすべてのリポジトリ」は、組織の接続（GitHub App のインストール）で miruca が許可されたリポジトリすべてを指す。
- 1人のユーザーが、管理者でもあり、GitHub のアカウントも持つことがある。そのときは見られる範囲の和をとる。
- 判定は API の1か所（`visibleRepositories(user, organization)`）にまとめる。一覧（F4）とリードタイム（F5）は、どちらもこの判定を使う。

## 認証の仕組み

### ログイン手段

| | GitHub でログイン | メールアドレスでログイン |
| --- | --- | --- |
| 使う人 | 開発者、組織の管理者 | マネージャー（GitHub のアカウントを持たない人） |
| miruca に入る条件 | 招待はいらない。GitHub でログインすれば入れる | 管理者に招待されたメールアドレスだけ |
| 本人の確かめ方 | GitHub App のユーザー認可（OAuth の流れ） | 1回きりのログイン用のリンクをメールで送る |
| 見られる範囲 | 「見られる範囲」の表のとおり | 同じ |

どちらでログインしても、ログインした後は同じセッションを使い、同じ `visibleRepositories` の判定を通る。

### GitHub でログインする流れ

1. `GET /api/auth/github/login` が、推測できない `state` を作る。`state` は10分で切れる HttpOnly の cookie に入れ、GitHub の認可画面へリダイレクトする。
2. 使う人が GitHub の画面で許可すると、GitHub が `GET /api/auth/github/callback` に `code` と `state` を付けて戻す。
3. `state` を cookie の値と照合する。一致しなければログインを失敗にする。
4. `code` をユーザーのアクセストークンとリフレッシュトークンに交換し、`GET /user` で GitHub のアカウントを取る。
5. 初めての GitHub アカウントなら、miruca のユーザーを作り、ログイン手段として紐づける。2回目からは紐づいたユーザーとしてログインする。
6. セッションを作る（「セッション」を参照）。

- GitHub のトークンは DynamoDB に置き、ブラウザには渡さない。
- アクセストークンの期限が切れていたら、リフレッシュトークンで取り直す。取り直せなければ、そのセッションを消してログイン画面に戻す。

### メールアドレスでログインする流れ

1. ログイン画面でメールアドレスを入れると、`POST /api/auth/email/link` を呼ぶ。
2. 招待されているメールアドレスなら、ログイン用のリンクをメールで送る。リンクに入れるトークンは乱数（32バイト）で作り、DynamoDB にはハッシュだけを置く。リンクは15分で切れ、1回だけ使える。
3. 招待されていないメールアドレスには、メールを送らない。画面にはどちらの場合も「メールを送りました」と出し、登録されているかを判別できないようにする。
4. 同じメールアドレスへの送信は、1時間に5回までにする。
5. 使う人がメールのリンクを開くと、「ログイン」ボタンだけの画面が出る。ボタンを押すと、トークンを `POST /api/auth/email/verify` で送る。
6. トークンのハッシュが一致し、期限内で未使用なら、使用済みにしてセッションを作る。

リンクを開いただけではログインしない。会社のメールのセキュリティ製品は、届いたメールのリンクを先に開いて中身を確かめることがあり、開いただけで1回きりのリンクが使われてしまうのを防ぐため。

### セッション

- ブラウザには、HttpOnly、Secure、SameSite=Lax の cookie `__Host-miruca_session` でセッション ID だけを渡す。ローカルでは http で動くので、`Secure` と `__Host-` を外す。
- セッション ID は暗号学的な乱数（32バイト）で作る。ログインのたびに新しい ID を発行し、ログイン前の ID は使い回さない。
- セッションは作ってから14日で切れる。切れたらログイン画面に戻す。期限切れのセッションは DynamoDB の TTL で消す。
- ログアウト（`POST /api/auth/logout`）すると、セッションを消し、cookie も消す。

### 認可

- API は、リクエストのたびに次の順で判定する。
  1. cookie のセッション ID からユーザーを引く。なければ 401。
  2. 所属と役割を DynamoDB から読む。所属と役割はセッションに持たせない。所属を解除したら、次のリクエストから見られなくなる。
  3. リポジトリを扱う API は `visibleRepositories` で判定し、見てはいけなければ 404 を返す。存在するかどうかを知らせないため、403 ではなく 404 にする。
  4. 管理者だけの API（招待、所属の解除）は、管理者でなければ 403 を返す。
- 状態を変える API（POST、DELETE）は、cookie の SameSite に加えて、リクエストの `Origin` が miruca の URL であることを確かめる。

### 1人が両方のログイン手段を持つ場合

GitHub のアカウントを持つ人が、メールアドレスでも招待されることがある。0.1 では、2つのログイン手段を1人のユーザーにまとめない。GitHub でログインしたときとメールでログインしたときは、別々の miruca のユーザーになる。管理者には、GitHub のアカウントがある人は招待せずに管理者にするよう、招待の画面で案内する。

データの形は1人のユーザーが複数のログイン手段を持てる作りなので、0.1 の次で「ログイン後に、もう一方のログイン手段をつなぐ」機能を足せる。

### ローカルでのログイン

`MIRUCA_ENV=local` のときだけ、ログイン画面に「開発者として入る」「マネージャーとして入る」「管理者として入る」を出す（「ローカルでの起動」を参照）。この API は Lambda にデプロイするコードには登録されないことを、テストで確かめる。

## GitHub との連携

### GitHub App の設定

| 項目 | 値 |
| --- | --- |
| 権限 | リポジトリの Pull requests の読み取り、Metadata の読み取りだけ。組織の権限と、リポジトリの中身（Contents）は求めない |
| インストール時のユーザー認可 | 求める（Request user authorization during installation） |
| コールバック URL | CloudFront の URL + `/api/auth/github/callback`。開発用の App は `http://localhost:5173/api/auth/github/callback` |
| Webhook | 0.1 では使わない |
| 公開範囲 | Any account（ほかの組織がインストールできる）。GitHub Marketplace には載せない |

### 組織をつなぐ流れ

1. GitHub でログインした人が、miruca の「組織をつなぐ」を押す。`GET /api/connections/github/new` が `state` を作って cookie に入れ、`https://github.com/apps/<App の名前>/installations/new?state=...` へリダイレクトする。
2. 使う人が GitHub の画面で、インストール先の組織と、許可するリポジトリを選ぶ。
   - 組織のオーナーか、組織の権限を求めない App を入れられるリポジトリの管理者なら、そのままインストールできる。
   - それ以外の人は、オーナーへのインストールの依頼になる。オーナーが承認するまで、miruca にはつながらない。
3. GitHub が `GET /api/auth/github/callback` に、`code`、`state`、`installation_id`、`setup_action` を付けて戻す。
4. `state` を照合し、`code` をユーザーのトークンに交換する（ログインと同じ）。
5. `installation_id` は URL に付いてくる値なので、そのまま信じない。ユーザーのトークンで `GET /user/installations` を呼び、その中にあることを確かめる。
6. インストール先の GitHub の組織が、miruca の利用を許可した組織かを確かめる（「利用の許可」を参照）。許可されていなければ、組織を作らず「miruca は招待制です」と出す。
7. miruca の組織と接続を作り（すでにあれば使う）、その人を管理者として所属させる。

この流れは GitHub の仕様についての理解に基づく。Issue 2 で、開発用の App を使って実際の戻り値（特に `setup_action` と、依頼したときの戻り方）を確かめてから実装する。

### 利用の許可

App の公開範囲は Any account なので、URL を知っていれば誰でもインストールできる。0.1 では、miruca を使ってよい GitHub の組織を DynamoDB に登録しておき、登録された組織のインストールだけを受け付ける。登録は運営者が手で行う。

登録されていない組織のインストールは、組織を作らず、データも取りに行かない。

### トークン

| トークン | 作り方 | 使い道 |
| --- | --- | --- |
| ユーザーのトークン | ログインのときに `code` から交換する | 本人の確認、`GET /user/installations`、開発者が見てよいリポジトリの判定 |
| インストールトークン | App の秘密鍵で署名した JWT（有効期限は最長10分）で `POST /app/installations/{installation_id}/access_tokens` を呼ぶ。有効期限は1時間 | リポジトリの一覧、PR のデータ。誰が見るときもこれを使う |

インストールトークンは期限までメモリに置いて使い回す。

### データの取り方

- リポジトリの一覧は、インストールトークンで `GET /installation/repositories` を呼んで取る。
- PR は、インストールトークンで GraphQL API の `search` を呼んで取る。検索条件は `repo:<owner>/<repo> is:pr is:merged merged:>=<30日前の日付>`。1回で100件ずつ、最大10回（1000件）取る。GitHub の検索は1つの条件で1000件までしか返さないので、1000件を超えたら画面にそのことを出す。
- `merged:` は日付単位でしか絞れないので、30 × 24 時間前より前にマージされた PR は、受け取った後に落とす。
- 取ったデータは保存しない。表示のたびに取る。

### つながりが切れたとき

組織のオーナーが App をアンインストールしたり、停止したりすると、インストールトークンを作れなくなる。0.1 では Webhook を使わないので、トークンを作るときの失敗で気づく。

- 接続を「切れている」状態にし、その組織の画面に「GitHub との接続が切れています。組織の管理者に確認してください」と出す。
- 管理者が「組織をつなぐ」をやり直すと、元の組織に戻る。
- 許可するリポジトリの変更は、次に一覧を取ったときに反映される。

## 機能要件

### F1. GitHub でログイン

- 「GitHub でログイン」から、GitHub のアカウントでログインできる（「GitHub でログインする流れ」）。
- ログインしている人は、ログアウトできる。

### F2. メールアドレスでログイン

- 招待された人は、メールで届くリンクからログインできる（「メールアドレスでログインする流れ」）。
- 招待メールのリンクは、メールアドレスを入れたログイン画面を開く。

### F3. 招待と管理者

- 組織の管理者は、メールアドレスを入れてマネージャーを招待できる。招待すると、その組織に「全体を見る人」として所属する。
- 招待メールには、組織の名前と、ログイン画面へのリンクを入れる。
- 招待は7日で切れる。切れた招待は、管理者がもう一度送り直せる。
- 管理者は、招待中の人と所属している人の一覧を見られ、招待の取り消しと、所属の解除ができる。
- 管理者は、miruca に GitHub でログインしたことがある人を、管理者にできる。最後の1人の管理者は外せない。
- 管理者でない人には、招待の画面を出さない。

### F4. 組織とリポジトリの一覧

- GitHub でログインした人は、「組織をつなぐ」から組織に App をインストールできる（「組織をつなぐ流れ」）。
- 一覧には `visibleRepositories` が返すリポジトリだけを出す。
- miruca を通さずにインストールされた App も、利用を許可した組織なら、初めて見えたときに組織と接続を作る。このとき管理者はいない。管理者は、その組織で「組織をつなぐ」をやり直した人がなる。
- 一覧が空のときは、その人の立場に合わせて案内を出す。
  - GitHub でログインした人: 「所属する組織に miruca がインストールされていません」と表示し、「組織をつなぐ」ボタンと、管理者にインストールを頼むための URL を出す。
  - メールアドレスでログインした人: 「所属している組織がありません」と表示し、招待した人に確認するよう案内する。

### F5. PR リードタイム

- 対象は、選んだリポジトリで直近30日（今の時刻から 30 × 24 時間前まで）にマージされた PR。
- リードタイムは「PR を作った時刻からマージされた時刻まで」とする。ドラフトだった期間も含める。
- 画面には次のものを出す。
  - 対象の PR の件数
  - リードタイムの中央値（時間単位、小数第1位まで）
  - PR の一覧（番号、タイトル、作成者、リードタイム、元のサービスへのリンク）。リードタイムの長い順に並べる
- GitHub のアカウントでログインしていない人には、PR へのリンクの代わりに PR の番号だけを出す。GitHub のアカウントがない人には開けないため。
- 対象の PR が0件のときは、「直近30日にマージされた PR はありません」と表示する。
- 1000件を超えたら、集計が最新の1000件分であることを画面に表示する。

## データの形

```ts
type Provider = 'github';

type User = {
  userId: string;
  displayName: string;
};

type Identity =
  | {
      kind: 'github';
      userId: string;
      externalId: string;
      login: string;
      accessToken: string;
      accessTokenExpiresAt: string;
      refreshToken: string;
      refreshTokenExpiresAt: string;
    }
  | {
      kind: 'email';
      userId: string;
      email: string;
    };

type Session = {
  sessionId: string;
  userId: string;
  expiresAt: string;
};

type LoginLink = {
  tokenHash: string;
  email: string;
  expiresAt: string;
};

type Organization = {
  organizationId: string;
  name: string;
};

type Connection = {
  connectionId: string;
  organizationId: string;
  provider: Provider;
  externalId: string;
  status: 'active' | 'disconnected';
};

type AllowedAccount = {
  provider: Provider;
  externalId: string;
  login: string;
};

type Membership = {
  organizationId: string;
  userId: string;
  role: 'admin' | 'viewer';
};

type Invitation = {
  invitationId: string;
  organizationId: string;
  email: string;
  invitedBy: string;
  expiresAt: string;
};

type Repository = {
  repositoryId: string;
  connectionId: string;
  externalId: string;
  fullName: string;
};

type LeadTimeReport = {
  repository: { repositoryId: string; fullName: string };
  since: string;
  until: string;
  count: number;
  truncated: boolean;
  medianHours: number | null;
  pullRequests: {
    number: number;
    title: string;
    author: string;
    url: string | null;
    createdAt: string;
    mergedAt: string;
    leadTimeHours: number;
  }[];
};
```

- `Membership.role` の `viewer` が「全体を見る人」。GitHub でログインした開発者には `Membership` を作らず、GitHub 上のアクセス権で判定する。
- `provider` と `externalId` の組で、外部サービス側の ID を持つ。miruca の中で別のデータを指すときは、miruca の ID を使う。
- GitHub API の応答は API の入り口でこれらの型に変換し、画面には GitHub の生の応答を渡さない。

## API

| メソッドとパス | 役割 |
| --- | --- |
| `GET /api/auth/github/login` | GitHub の認可画面へリダイレクトする |

## インフラの変更

0.1 では次のものを足す。どれも IAM の権限を広げるか、リソースを足す変更なので、該当する Issue に明記する。

- ユーザー、ログイン手段、セッション、ログイン用のリンク、組織、接続、所属、招待、リポジトリ、利用を許可した組織を保存する DynamoDB テーブル（セッション、ログイン用のリンク、招待は TTL で期限切れを消す）
- GitHub App の client ID、client secret、秘密鍵を置く Secrets Manager のシークレット
- 招待メールとログイン用のリンクを送る Amazon SES（送信元ドメインの認証を含む）
- API の Lambda が、このテーブルを読み書きし、シークレットを読み、SES でメールを送るための IAM 権限

人が1回だけ行う準備は次のとおり。

- GitHub App を作る。設定は「GitHub App の設定」の表のとおり。
- GitHub App は、個人のアカウントではなく miruca 用の GitHub の組織の下に作る。公開範囲は「Any account」にして、ほかの組織がインストールできるようにする。GitHub Marketplace への掲載は 0.1 ではしない。
- 本番用と開発用で、GitHub App を別々に作る。秘密鍵と client secret を本番と分けるため。
- 権限を後から増やすと、インストール済みの組織ごとに承認が要る。0.1 で決めた権限で足りるように、指標を増やすときに権限が要るかを先に確かめる。
- SES で送信元のドメインを認証し、サンドボックスの解除を申請する。

## 将来の拡張に向けた前提

将来、次のものを足す。

- Google、Microsoft、SAML など、メールアドレス以外のログイン手段。
- 招待した人に見せる範囲を、一部のリポジトリやチームに絞ること。
- GitLab など、GitHub 以外のサービスへの対応。

0.1 の時点で次のことを守り、足すときに作り直しが要らないようにする。

- **ユーザーは miruca が持つ。** GitHub のアカウントもメールアドレスも、ユーザーに紐づくログイン手段の1つにする。ログイン手段を足すときは、`Identity` の種類を1つ足す。
- **組織は miruca が持つ。** GitHub App のインストールは、組織の接続の1つにする。GitLab は `Connection` の `provider` を足して扱う。
- **見てよいかの判定を1か所にまとめる。** 見せる範囲を絞るときは、`Membership` に範囲を持たせ、`visibleRepositories` を変える。
- **データは接続の権限で取る。** GitHub のアカウントがない人の分も、インストールトークンで取る。将来の定期収集も、同じトークンでログインした人なしに動く。
- **外部サービスの形は入り口で止める。** GitHub の応答は入り口で miruca の型に変換し、API のパスと画面には miruca の ID を使う。

0.1 では、GitHub と GitLab を切り替えるための共通のインターフェースは作らない。実装が GitHub の1つしかないうちは、型の変換だけを入り口に置く。インターフェースは、GitLab に対応するときに2つの実装を見て決める。

## ローカルでの起動

人も AI も、AWS と GitHub がなくても 0.1 の全部の画面を手元で動かして確かめられるようにする。今の `npm run dev:api` と `npm run dev:web` の2つで起動する形は変えない。

AWS と GitHub に頼る部分は、`MIRUCA_ENV=local` のときだけ次のものに置き換える。

| 本番 | ローカル | 理由 |
| --- | --- | --- |
| DynamoDB | DynamoDB Local | 本番と同じコードで読み書きを確かめるため。保存のコードを2つ持たない |
| Secrets Manager | `.env.local` | 開発用の GitHub App の値を置く。リポジトリにはコミットしない |
| Amazon SES | メールを送らず、本文とリンクを API のログに出す | 招待とメールでのログインを、メールなしで最後まで進められるようにするため |
| GitHub | 次の2つから選ぶ | |
| | **サンプルの GitHub。** 決まった組織、リポジトリ、PR を返す | GitHub のアカウントも App もなしで、全部の画面を確かめるため。テストでも同じデータを使う |
| | **開発用の GitHub App。** 本物の GitHub につなぐ | GitHub との連携そのものを確かめるため |
| CloudFront の `/api/*` の振り分け | Vite の proxy（今のまま） | |

- サンプルの GitHub は、「GitHub の入り口」と同じ型を返すもう1つの実装にする。判定と計算のコードは、どちらにつながっているかを知らない。
- ローカルでは、ログイン画面に「開発者として入る」「マネージャーとして入る」「管理者として入る」を出す。サンプルの GitHub のときに、立場を切り替えて確かめるため。
- このローカル専用のログインは、`MIRUCA_ENV=local` のときだけ API に登録する。Lambda にデプロイするコードでは登録されないことを、テストで確かめる。
- 開発用の GitHub App のコールバック URL には `http://localhost:5173/api/auth/github/callback` を登録する。

## 成功の基準

- 組織の管理者がインストールしてから、開発者が最初の数字を見るまで、追加の設定なしでたどり着ける。
- 管理者が招待してから、マネージャーが GitHub のアカウントなしで組織全体の数字を見るまで、招待メールとログインメールの2通だけでたどり着ける。
- miruca の数字が、GitHub の PR の作成時刻とマージ時刻から手で計算した値と一致する。
- 見られる範囲の外のリポジトリの数字は、URL を直接打っても見られない。所属を解除された人も見られない。

## Issue の分け方

0. ローカルで起動できるようにする。DynamoDB Local、サンプルの GitHub、ログに出すメール、ローカル専用のログインと、それが使うユーザーとセッションの保存を用意する（「ローカルでの起動」、共通）。DynamoDB を読み書きする AWS SDK の追加を、この Issue に明記する。
1. GitHub でログイン、ログアウトする。GitHub のログイン手段を保存する（F1）。
2. 組織とリポジトリの一覧を出す。組織、接続、リポジトリを保存し、miruca からインストールした人を管理者にする（F4、`visibleRepositories`）。
3. 選んだリポジトリの PR リードタイムを出す（F5）。
4. メールアドレスでログインする（F2）。
5. マネージャーを招待し、「全体を見る人」として所属させる（F3）。

インフラの変更は、そのテーブルやシークレット、SES を最初に使う Issue に入れる。0 を最初に入れる。1 から 5 は、それぞれローカルで動くところまでを受け入れ条件に含める。4 と 5 は、1 から 3 と並行して進められる。
