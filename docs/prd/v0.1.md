# PRD: miruca 0.1

全体の構成図は [docs/architecture.md](../architecture.md) にある。

## 目的

miruca は、チームの開発の流れをコードホスティングサービスのデータから数字で見せるサービスです。0.1 では、開発者が GitHub でログインして自分のリポジトリの PR リードタイムを見られることと、GitHub のアカウントを持たないマネージャーが組織のすべてのリポジトリの PR リードタイムを見られることを作ります。

0.1 で確かめたいのは次の3つです。

- GitHub App のインストールから最初の数字を見るまでの流れが、組織の管理者と開発者にとって迷わないか。
- 招待されたマネージャーが、GitHub のアカウントなしで、組織全体の数字までたどり着けるか。
- 1つの数字（PR リードタイム）が、チームとマネージャーが振り返りに使える形で出せるか。

## 使う人

| 人 | GitHub のアカウント | やること |
| --- | --- | --- |
| 組織の管理者 | ある（miruca から GitHub App をインストールした人） | 組織に miruca の GitHub App をインストールする。マネージャーを招待する。組織のすべてのリポジトリを見る |
| 開発者 | ある | GitHub でログインし、GitHub 上でアクセスできるリポジトリの数字を見る |
| マネージャー | ない | 招待メールからメールアドレスでログインし、組織のすべてのリポジトリの数字を見る |

## 範囲

### 0.1 に入れるもの

1. GitHub でログインする、ログアウトする。
2. メールアドレスでログインする（招待された人だけ）。
3. 組織の管理者が、メールアドレスを指定してマネージャーを招待する。招待を取り消す。
4. 自分が見られる組織とリポジトリの一覧を見る。
5. 選んだリポジトリの、直近30日にマージされた PR のリードタイムを見る。

### 0.1 に入れないもの

- メールアドレス以外の、GitHub を使わないログイン手段（Google、Microsoft、SAML など）。
- 招待した人を、一部のリポジトリやチームだけに絞って見せること。
- GitLab など GitHub 以外のサービスへの対応。
- 定期的なデータ収集と保存。表示のたびに GitHub API を呼ぶ。
- 複数のリポジトリをまとめた集計、チーム単位の集計。
- PR リードタイム以外の指標（レビュー時間、スループット、DORA）。
- グラフ、期間の切り替え、CSV の出力。
- 課金。

最初の3つは、0.1 の作りで後から足せるようにする（「将来の拡張に向けた前提」を参照）。残りは 0.1 を使った人の反応を見てから、別の PRD か Issue で扱う。

## 使う人の流れ

### 組織の管理者

1. miruca を開き、「GitHub でログイン」を押す。
2. 「組織をつなぐ」から GitHub App「miruca」を組織にインストールし、対象のリポジトリを選ぶ。
3. miruca に戻ると、その人がつないだ組織の管理者になり、組織のすべてのリポジトリが一覧で出る。
4. 「メンバーを招待」からマネージャーのメールアドレスを入れて招待する。

### 開発者

1. miruca を開き、「GitHub でログイン」を押す。
2. GitHub 上でアクセスできるリポジトリが一覧で出る。
3. リポジトリを選ぶと、PR リードタイムが出る。

### マネージャー

1. 招待メールのリンクを開く。
2. 「ログイン用のリンクを送る」を押す。届いたメールのリンクを開くとログインできる。
3. 組織のすべてのリポジトリが一覧で出る。
4. リポジトリを選ぶと、PR リードタイムが出る。

2回目からは、miruca のログイン画面でメールアドレスを入れ、届いたリンクからログインする。

## 用語

| 用語 | 意味 |
| --- | --- |
| ユーザー | miruca に登録された人。miruca が ID を発行する。GitHub のアカウントとは別のもの |
| ログイン手段 | ユーザーがログインに使うもの。0.1 では GitHub のアカウントとメールアドレスの2種類 |
| 組織 | miruca 上の会社やチームの単位。miruca が ID を発行する |
| 接続 | 組織とコードホスティングサービスのつながり。0.1 では GitHub App のインストール |
| 所属 | ユーザーが組織で持つ役割。0.1 では「管理者」と「全体を見る人」の2種類 |
| リポジトリ | 接続を通して見えるリポジトリ。miruca が ID を発行する |
| PR | GitHub の Pull Request。将来は GitLab の Merge Request も PR として扱う |

## 見られる範囲

| 人 | 所属 | 見られるリポジトリ |
| --- | --- | --- |
| 組織の管理者 | 管理者 | 組織のすべてのリポジトリ |
| マネージャー | 全体を見る人 | 組織のすべてのリポジトリ |
| 開発者 | なし | GitHub 上でアクセスできるリポジトリ |

- 「組織のすべてのリポジトリ」は、組織の接続（GitHub App のインストール）で miruca が許可されたリポジトリすべてを指す。
- 1人のユーザーが、管理者でもあり、GitHub のアカウントも持つことがある。そのときは見られる範囲の和をとる。
- 判定は API の1か所（`visibleRepositories(user, organization)`）にまとめる。一覧（F4）とリードタイム（F5）は、どちらもこの判定を使う。

## 機能要件

### F1. GitHub でログイン

- GitHub App のユーザー認可（OAuth の流れ）でログインする。
- 認可の要求には `state` を付け、戻ってきたときに照合する。一致しなければログインを失敗にする。
- 初めてログインした GitHub アカウントには、miruca のユーザーを作り、ログイン手段として GitHub アカウントを紐づける。2回目からは紐づいたユーザーとしてログインする。
- GitHub のトークン（アクセストークンとリフレッシュトークン）はサーバー側に保存し、ブラウザには渡さない。
- アクセストークンの期限が切れていたら、リフレッシュトークンで取り直す。取り直せなければログアウトした状態にし、ログイン画面に戻す。
- GitHub App は、インストールのときにユーザー認可も求める設定にする。miruca から「組織をつなぐ」を押してインストールした人を、その組織の管理者にする。インストールの ID がその人の `GET /user/installations` に含まれることを確かめてから管理者にする。
- 管理者は、ほかの GitHub ユーザーを管理者にできる。最後の1人の管理者は外せない。

### F2. メールアドレスでログイン

- ログイン画面でメールアドレスを入れると、ログイン用のリンクをメールで送る。
- リンクは1回だけ使え、15分で切れる。リンクに含めるトークンは、サーバー側にはハッシュだけを保存する。
- 招待されていないメールアドレスでも、画面には同じ「メールを送りました」を出す。登録されているかどうかを画面から判別できないようにする。招待されていないアドレスには、メールを送らない。
- 同じメールアドレスへの送信は、1時間に5回までにする。

### F3. 招待

- 組織の管理者は、メールアドレスを入れてマネージャーを招待できる。招待すると、その組織に「全体を見る人」として所属する。
- 招待メールには、組織の名前と、ログイン画面へのリンクを入れる。
- 招待は7日で切れる。切れた招待は、管理者がもう一度送り直せる。
- 管理者は、招待中の人と所属している人の一覧を見られ、招待の取り消しと、所属の解除ができる。解除した人の既存のセッションは、その組織のデータを見られなくなる。
- 管理者でない人には、招待の画面を出さず、API も 403 を返す。

### F4. 組織とリポジトリの一覧

- miruca を通さずにインストールされた GitHub App も、初めて見えたときに miruca の組織と接続を作る。管理者はいない状態になり、開発者は GitHub の権限で見られる。管理者は、その組織に miruca から「組織をつなぐ」をもう一度行った人がなる。初めて見えたリポジトリにも miruca の ID を発行する。
- リポジトリの一覧は、GitHub App のインストールトークンで `GET /installation/repositories` を呼んで取る。
- 開発者の分は、ログインした人の GitHub のトークンで `GET /user/installations` と `GET /user/installations/{installation_id}/repositories` を呼び、アクセスできるものに絞る。
- 一覧には `visibleRepositories` が返すリポジトリだけを出す。
- 一覧が空のときは、その人の立場に合わせて案内を出す。
  - GitHub でログインした人: 「所属する組織に miruca がインストールされていません」と表示し、管理者にインストールを頼むための URL を出す。
  - メールアドレスでログインした人: 「所属している組織がありません」と表示し、招待した人に確認するよう案内する。

### F5. PR リードタイム

- PR のデータは GitHub App のインストールトークンで取る。見てよいかは `visibleRepositories` で先に判定し、見てはいけなければ 404 を返す。
- 対象は、選んだリポジトリで直近30日（今の時刻から 30 × 24 時間前まで）にマージされた PR。
- リードタイムは「PR を作った時刻からマージされた時刻まで」とする。ドラフトだった期間も含める。
- 画面には次のものを出す。
  - 対象の PR の件数
  - リードタイムの中央値（時間単位、小数第1位まで）
  - PR の一覧（番号、タイトル、作成者、リードタイム、元のサービスへのリンク）。リードタイムの長い順に並べる
- PR へのリンクは、GitHub のアカウントがない人には開けない。GitHub のアカウントでログインしていない人には、リンクの代わりに PR の番号だけを出す。
- 対象の PR が0件のときは、「直近30日にマージされた PR はありません」と表示する。
- 集計する PR は最大1000件とする。1000件を超えたら、集計が最新の1000件分であることを画面に表示する。

### 共通

- セッションは、ブラウザには HttpOnly、Secure、SameSite=Lax の cookie でセッション ID だけを渡す。
- ログアウトするとセッションを消し、cookie も消す。
- 状態を変える API（POST、DELETE）は、cookie だけでは受け付けない。リクエストの `Origin` が miruca の URL であることを確かめる。

## データの形

```ts
type Provider = 'github';

type User = {
  userId: string;
  displayName: string;
};

type Identity =
  | {
      kind: 'github';
      userId: string;
      externalId: string;
      login: string;
      accessToken: string;
      accessTokenExpiresAt: string;
      refreshToken: string;
      refreshTokenExpiresAt: string;
    }
  | {
      kind: 'email';
      userId: string;
      email: string;
    };

type Session = {
  sessionId: string;
  userId: string;
  expiresAt: string;
};

type LoginLink = {
  tokenHash: string;
  email: string;
  expiresAt: string;
};

type Organization = {
  organizationId: string;
  name: string;
};

type Connection = {
  connectionId: string;
  organizationId: string;
  provider: Provider;
  externalId: string;
};

type Membership = {
  organizationId: string;
  userId: string;
  role: 'admin' | 'viewer';
};

type Invitation = {
  invitationId: string;
  organizationId: string;
  email: string;
  invitedBy: string;
  expiresAt: string;
};

type Repository = {
  repositoryId: string;
  connectionId: string;
  externalId: string;
  fullName: string;
};

type LeadTimeReport = {
  repository: { repositoryId: string; fullName: string };
  since: string;
  until: string;
  count: number;
  truncated: boolean;
  medianHours: number | null;
  pullRequests: {
    number: number;
    title: string;
    author: string;
    url: string | null;
    createdAt: string;
    mergedAt: string;
    leadTimeHours: number;
  }[];
};
```

- `Membership.role` の `viewer` が「全体を見る人」。GitHub でログインした開発者には `Membership` を作らず、GitHub 上のアクセス権で判定する。
- `provider` と `externalId` の組で、外部サービス側の ID を持つ。miruca の中で別のデータを指すときは、miruca の ID を使う。
- GitHub API の応答は API の入り口でこれらの型に変換し、画面には GitHub の生の応答を渡さない。

## API

| メソッドとパス | 役割 |
| --- | --- |
| `GET /api/auth/github/login` | GitHub の認可画面へリダイレクトする |
| `GET /api/auth/github/callback` | 認可コードをトークンに交換し、ユーザーとセッションを作る |
| `POST /api/auth/email/link` | ログイン用のリンクをメールで送る |
| `GET /api/auth/email/callback` | リンクのトークンを確かめ、セッションを作る |
| `POST /api/auth/logout` | セッションを消す |
| `GET /api/me` | ログインしているユーザーの `userId`、`displayName`、ログイン手段の種類を返す。未ログインなら 401 |
| `GET /api/organizations` | 見られる組織と、その中の見られるリポジトリ、その組織での自分の役割を返す |
| `GET /api/organizations/:organizationId/members` | 所属している人と招待中の人を返す。管理者だけ |
| `POST /api/organizations/:organizationId/invitations` | 招待する。管理者だけ |
| `DELETE /api/organizations/:organizationId/invitations/:invitationId` | 招待を取り消す。管理者だけ |
| `DELETE /api/organizations/:organizationId/members/:userId` | 所属を解除する。管理者だけ |
| `GET /api/repositories/:repositoryId/lead-time` | `LeadTimeReport` を返す。その人が見られないリポジトリなら 404 |

## インフラの変更

0.1 では次のものを足す。どれも IAM の権限を広げるか、リソースを足す変更なので、該当する Issue に明記する。

- ユーザー、ログイン手段、セッション、ログイン用のリンク、組織、接続、所属、招待、リポジトリを保存する DynamoDB テーブル（セッション、ログイン用のリンク、招待は TTL で期限切れを消す）
- GitHub App の client ID、client secret、秘密鍵を置く Secrets Manager のシークレット
- 招待メールとログイン用のリンクを送る Amazon SES（送信元ドメインの認証を含む）
- API の Lambda が、このテーブルを読み書きし、シークレットを読み、SES でメールを送るための IAM 権限

人が1回だけ行う準備は次のとおり。

- GitHub App を作り、コールバック URL（CloudFront の URL + `/api/auth/github/callback`）を登録する。権限は、リポジトリの Pull requests と Metadata の読み取りだけにする。組織の権限は求めない。組織の権限を求めない App は、組織のオーナーでなくてもリポジトリの管理者がインストールできる（オーナーが禁止していなければ）。リポジトリの中身（Contents）も読まない。
- GitHub App は、個人のアカウントではなく miruca 用の GitHub の組織の下に作る。公開範囲は「Any account」にして、ほかの組織がインストールできるようにする。GitHub Marketplace への掲載は 0.1 ではしない。
- 本番用と開発用で、GitHub App を別々に作る。秘密鍵と client secret を本番と分けるため。
- 権限を後から増やすと、インストール済みの組織ごとに承認が要る。0.1 で決めた権限で足りるように、指標を増やすときに権限が要るかを先に確かめる。
- SES で送信元のドメインを認証し、サンドボックスの解除を申請する。

## 将来の拡張に向けた前提

将来、次のものを足す。

- Google、Microsoft、SAML など、メールアドレス以外のログイン手段。
- 招待した人に見せる範囲を、一部のリポジトリやチームに絞ること。
- GitLab など、GitHub 以外のサービスへの対応。

0.1 の時点で次のことを守り、足すときに作り直しが要らないようにする。

- **ユーザーは miruca が持つ。** GitHub のアカウントもメールアドレスも、ユーザーに紐づくログイン手段の1つにする。ログイン手段を足すときは、`Identity` の種類を1つ足す。
- **組織は miruca が持つ。** GitHub App のインストールは、組織の接続の1つにする。GitLab は `Connection` の `provider` を足して扱う。
- **見てよいかの判定を1か所にまとめる。** 見せる範囲を絞るときは、`Membership` に範囲を持たせ、`visibleRepositories` を変える。
- **データは接続の権限で取る。** GitHub のアカウントがない人の分も、インストールトークンで取る。将来の定期収集も、同じトークンでログインした人なしに動く。
- **外部サービスの形は入り口で止める。** GitHub の応答は入り口で miruca の型に変換し、API のパスと画面には miruca の ID を使う。

0.1 では、GitHub と GitLab を切り替えるための共通のインターフェースは作らない。実装が GitHub の1つしかないうちは、型の変換だけを入り口に置く。インターフェースは、GitLab に対応するときに2つの実装を見て決める。

## 成功の基準

- 組織の管理者がインストールしてから、開発者が最初の数字を見るまで、追加の設定なしでたどり着ける。
- 管理者が招待してから、マネージャーが GitHub のアカウントなしで組織全体の数字を見るまで、招待メールとログインメールの2通だけでたどり着ける。
- miruca の数字が、GitHub の PR の作成時刻とマージ時刻から手で計算した値と一致する。
- 見られる範囲の外のリポジトリの数字は、URL を直接打っても見られない。所属を解除された人も見られない。

## Issue の分け方

1. GitHub でログイン、ログアウトする。ユーザー、ログイン手段、セッションを保存する（F1、共通）。
2. 組織とリポジトリの一覧を出す。組織、接続、リポジトリを保存し、GitHub の組織のオーナーを管理者にする（F4、`visibleRepositories`）。
3. 選んだリポジトリの PR リードタイムを出す（F5）。
4. メールアドレスでログインする（F2）。
5. マネージャーを招待し、「全体を見る人」として所属させる（F3）。

インフラの変更は、そのテーブルやシークレット、SES を最初に使う Issue に入れる。4 と 5 は、1 から 3 と並行して進められる。

## 未決事項

PRD を書いた時点で、次のことは仮に決めている。変えるときはこの PRD を直してから Issue を書く。

| 項目 | 仮の決定 | ほかの案 |
| --- | --- | --- |
| マネージャーのログイン手段 | メールで届くログイン用のリンク | Google、Microsoft のアカウント。会社が使っているものに合わせられるが、使っていない会社では使えない |
| 組織の管理者 | miruca から GitHub App をインストールした人 | GitHub の組織のオーナー（組織の Members の読み取り権限が要り、オーナーしかインストールできなくなる） |
| 0.1 の組織 | GitHub のインストール1つにつき、miruca の組織1つ（類似プロダクトは複数をまとめる形が多い。`docs/research/similar-products.md`） | 1つの組織に複数のインストールをまとめる。会社が GitHub の組織を複数持っていて、マネージャーが全部まとめて見たい場合に必要 |
| 開発者を miruca で招待するか | しない。GitHub でログインすれば見られる | 管理者が招待した人だけが使える |
| 最初の指標 | PR リードタイム | レビュー時間、スループット |
| リードタイムの起点 | PR を作った時刻 | PR の最初のコミットの時刻 |
| ボットの PR | 含める | Dependabot などを除く |
| GitHub の IP 許可リストを使う組織 | 0.1 では対応しない | API の送信元 IP を固定し（NAT ゲートウェイと Elastic IP）、GitHub App に登録する |
| GitLab に対応する時期 | 未定（0.1 では作らない） | 0.1 の次、指標を増やした後 |
